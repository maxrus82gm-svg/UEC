# СТАРТ АГЕНТА

Краткий маршрутизатор постоянных правил для работы с проектом C++ / Unreal Engine.

## 1. Что читать всегда

Перед любой задачей агент читает:

- Documentation_CPP_UE/11_Задача_агенту.md;
- Documentation_CPP_UE/12_Старт_агента.md.

Дополнительные SplitDoc выбираются по матрице в task-loop. Project_Docs читаются только по прямому указанию текущей задачи.

## 2. Выборочное чтение

ChatGPT перед постановкой задачи:

1. определяет тему;
2. выбирает минимальный достаточный набор SplitDoc;
3. перечисляет его в разделе «Читать» БЛОКА 1;
4. не направляет агента читать всю базу на всякий случай;
5. не копирует постоянные правила в задачу, если достаточно ссылки на канонический документ.

Агент не расширяет набор документов без причины. Если нужного правила или факта нет, это отмечается как вопрос или проблема, а не заменяется догадкой.

## 3. Роли

Пользователь:

- принимает финальные решения;
- контролирует Git;
- выполняет или подтверждает проверки, недоступные агенту.

ChatGPT:

- формирует безопасный TASK и маршрутизирует чтение;
- задаёт scope, разрешённые и запрещённые файлы;
- после AGENT REPORT при возможности проверяет фактический результат, а не принимает только текст отчёта;
- фиксирует review/status.

Агент:

- выполняет только активную задачу;
- меняет только разрешённые файлы;
- проводит доступные проверки;
- честно сообщает ограничения и проблемы вне scope;
- не меняет архитектуру без отдельной задачи.

## 4. Кодировка

Для любых изменений текстовых файлов с кириллицей обязательно читать Documentation_CPP_UE/20_SplitDoc/ENCODING_RULES.md.

Новые и нормализованные Markdown-документы сохраняются в UTF-8 без BOM. Нечитаемый русский текст нельзя угадывать или перезаписывать. При признаках повреждения работа с этим участком останавливается до определения причины и надёжного источника текста.

## 5. Активная задача и очистка БЛОКА 1

Активная задача находится только в БЛОКЕ 1 файла Documentation_CPP_UE/11_Задача_агенту.md.

После успешного выполнения агент:

1. обновляет БЛОК 2 отчётом;
2. обновляет TASK_HISTORY, если это разрешено задачей;
3. при необходимости устанавливает БЛОК 3 в состояние ожидания review;
4. удаляет из БЛОКА 1 текст завершённой TASK;
5. оставляет существующий заголовок БЛОКА 1 и ровно три смысловые строки:

   Активной задачи нет.  
   Предыдущая задача выполнена.  
   Ожидается новая задача от пользователя.

6. сохраняет разделитель и заголовок БЛОКА 2.

Self-check после очистки:

- заголовок БЛОКА 1 существует один раз;
- номер и текст завершённой задачи в БЛОКЕ 1 отсутствуют;
- три строки заглушки присутствуют;
- БЛОК 2 не удалён и содержит отчёт.

При статусе BLOCKED или незавершённой задаче БЛОК 1 автоматически не очищается.

## 6. Границы задачи

1. Аналитическая задача не превращается в правку.
2. Агент не делает инициативных изменений и не чинит соседние проблемы «заодно».
3. Меняются только явно разрешённые файлы и разделы.
4. Запрещённые файлы не меняются.
5. Пользовательские незакоммиченные изменения нельзя откатывать или перезаписывать.
6. Удаление, перенос, переименование, изменение публичных интерфейсов и архитектуры требуют прямой задачи.
7. Найденная проблема вне scope записывается в PROBLEMS, QUESTIONS или RECOMMENDED NEXT TASK.
8. Если безопасное выполнение требует выйти за scope, агент останавливает эту часть работы и запрашивает отдельное решение.

## 7. Уточнения после постановки задачи

Пока по активной задаче не получен AGENT REPORT, небольшое уточнение передаётся отдельным коротким сообщением и не требует переписывать БЛОК 1.

Сообщение содержит:

- путь Documentation_CPP_UE/11_Задача_агенту.md;
- ссылку на БЛОК 1;
- номер и название текущей TASK;
- само уточнение;
- указание, нужно ли менять файлы или только учесть информацию.

Если уточнение существенно меняет цель или scope, пользователь выбирает: продолжить текущую задачу, отменить её, переписать БЛОК 1 или оформить следующую TASK.

## 8. Куда агент может писать

По умолчанию агент пишет только в чат и в файлы, прямо разрешённые активной задачей.

Обновление task-loop, TASK_HISTORY, правил или Project_Docs разрешено только тогда, когда это входит в scope. Новое постоянное правило помещается в один наиболее подходящий канонический документ; в других местах добавляются только ссылки.

## 9. Git и review

Git контролирует пользователь. Полные правила: Documentation_CPP_UE/20_SplitDoc/GIT_REVIEW_RULES.md.

Без отдельной прямой команды агент не выполняет изменяющие Git-действия. Read-only Git используется только когда это нужно задаче или review.

При review фактические изменённые файлы сравниваются со scope. Все посторонние изменения, включая служебные, перечисляются в UNEXPECTED CHANGES. Пользовательские изменения не откатываются.

## 10. Документация

При создании или обновлении Markdown и постоянных правил читать:

- Documentation_CPP_UE/20_SplitDoc/DOCUMENTATION_RULES.md;
- Documentation_CPP_UE/20_SplitDoc/ENCODING_RULES.md.

START остаётся маршрутизатором. Тематические детали хранятся в SplitDoc и не дублируются здесь целиком.

## 11. Формат AGENT REPORT

Базовые разделы:

- TASK;
- STATUS;
- SOURCE или READ;
- CREATED FILES и/или CHANGED FILES;
- DONE или ADAPTED MECHANISMS;
- CHECKS;
- UNEXPECTED CHANGES или CHANGED OUTSIDE TARGET;
- PROBLEMS;
- QUESTIONS, если они есть;
- RECOMMENDED NEXT TASK, если уместно;
- GIT;
- CONCLUSION.

Отчёт перечисляет только реально выполненные проверки. Если compile, build, runtime, Git или внешний сервис не проверялись, это указывается прямо.

## 12. Постановка будущих задач

Обычная постановка задачи использует два отдельных сообщения:

1. Большой БЛОК 1 — полное техническое задание, помещаемое в Documentation_CPP_UE/11_Задача_агенту.md.
2. Малое стартовое сообщение агенту — номер и название TASK, путь к task-loop, указание на БЛОК 1, список документов для чтения и команда выполнить только текущую задачу.

Каждая новая задача получает номер TASK XXX. Номер не переиспользуется.

Большой блок задаёт:

- цель;
- минимальный контекст;
- что читать;
- что сделать;
- scope;
- разрешённые файлы;
- запреты;
- проверки;
- формат отчёта.

Малое сообщение не дублирует полное техническое задание.

Один TASK по возможности является одним законченным шагом. Большие исследования, архитектурные изменения и реализации разделяются на последовательные задачи, если это не нарушает целостность результата.

## 13. Unreal Engine и C++

Структуру проекта нельзя предполагать по шаблону. Перед проектными решениями читать соответствующий SplitDoc и фактические файлы в scope.

- Структура проекта и generated-каталоги: Documentation_CPP_UE/20_SplitDoc/UNREAL_PROJECT_RULES.md.
- Unreal C++: Documentation_CPP_UE/20_SplitDoc/UNREAL_CPP_RULES.md.

Не создавать параллельную архитектуру, не объявлять Blueprint временным и не считать успешную текстовую правку доказательством успешной сборки.
