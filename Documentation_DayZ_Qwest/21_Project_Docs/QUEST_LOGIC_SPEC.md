# QUEST LOGIC SPEC

Документ описывает базовую логику квестовой системы `Silver_77_Quests`.

Этот документ является источником истины для:

- игрового кода
- JSON-квестов
- редактора квестов
- задач для агентов

---

## 1. Главная модель

Каждый квест является независимой сущностью.

Один квест не должен случайно блокировать, завершать или изменять другой квест.

Каждый квест может иметь:

- `requiredQuestIds[]` — внешние зависимости от других квестов
- `Offer` — обязательный этап взятия квеста
- `Completion[]` — опциональные промежуточные этапы
- `Reward` — обязательный этап закрытия квеста и выдачи награды

Общая модель:

```text
Quest
├─ requiredQuestIds[]
├─ Offer
├─ Completion[]
└─ Reward
```

---

## 2. requiredQuestIds

`requiredQuestIds` описывает внешние зависимости между разными квестами.

Если `requiredQuestIds` пустой:

- у квеста нет зависимостей
- квест может быть виден и доступен без прохождения других квестов

Если `requiredQuestIds` не пустой:

- все указанные квесты должны иметь статус `completed`
- только после этого текущий квест может стать видимым и доступным для взятия

Важно:

- `requiredQuestIds` влияет только на доступность квеста
- `requiredQuestIds` не является Completion-этапом
- `requiredQuestIds` не должен использоваться для логики сдачи текущего квеста
- связи между разными квестами должны быть явными только через `requiredQuestIds`

Пример:

```text
quest_15 имеет requiredQuestIds: ["quest_12"]

Значит quest_15 не должен быть доступен,
пока quest_12 не завершён.
```

Русское название для редактора:

```text
Требуемые завершённые квесты
```

Описание для редактора:

```text
Если список пустой — квест доступен без прохождения других квестов.
Если список заполнен — все указанные квесты должны быть завершены,
иначе этот квест не будет доступен.
```

---

## 3. Offer

`Offer` — обязательный этап.

Offer определяет, где игрок может взять квест.

Offer:

- не закрывает квест
- не выдаёт финальную награду
- не считается Completion-этапом
- переводит квест в состояние `active`

Пример:

```text
Игрок берёт квест у Ворона.
offerTriggerIds содержит hunter_trigger.
```

JSON-поля, связанные с Offer:

```json
"offerTriggerIds": ["hunter_trigger"]
```

---

## 4. Completion

`Completion` — опциональный этап.

Completion используется только если у квеста есть промежуточные обязательные этапы.

Если Completion-этапов нет:

- Completion считается отсутствующим
- количество обязательных Completion-этапов равно `0`
- Reward может закрыть квест после выполнения основных условий / objectives

Если Completion-этапы есть:

- каждый Completion-блок относится только к текущему `questId`
- каждый Completion-блок должен быть выполнен
- пока выполнены не все Completion-блоки, Reward не должен закрывать квест

Логика счётчиков:

```text
requiredCompletionCount = количество Completion-блоков
completedCompletionCount = количество выполненных Completion-блоков
remainingCompletionCount = requiredCompletionCount - completedCompletionCount
```

Reward доступен только если:

```text
remainingCompletionCount == 0
```

Важно:

- пустой `completionTriggerIds` означает, что Completion-этапов нет
- пустой `completionTriggerIds` не должен означать, что квест нельзя сдавать нигде
- если Completion отсутствует, Reward должен иметь право закрыть квест
- Completion относится только к этапам внутри текущего квеста

JSON-поля, связанные с Completion:

```json
"completionTriggerIds": ["some_completion_trigger"]
```

---

## 5. Reward

`Reward` — обязательный этап.

Reward определяет, где квест закрывается и где игрок получает награду.

Reward:

- закрывает квест
- выдаёт награду
- переводит квест в состояние `completed`

Если Completion-этапов нет:

- Reward может закрыть квест напрямую после выполнения objectives

Если Completion-этапы есть:

- Reward может закрыть квест только после выполнения всех Completion-этапов

Если Completion-этапы ещё не выполнены:

- Reward должен быть недоступен
- UI должен объяснить, что сначала нужно выполнить промежуточные этапы

JSON-поля, связанные с Reward:

```json
"rewardTriggerIds": ["hunter_trigger"]
```

---

## 6. Простые квесты без Completion

Простой квест имеет схему:

```text
Offer -> Reward
```

Пример:

```text
Взять квест у Ворона.
Принести предметы Ворону.
Получить награду у Ворона.
```

Для такого квеста:

- Offer обязателен
- Completion отсутствует
- Reward обязателен
- `completionTriggerIds` может быть пустым
- `rewardTriggerIds` должен указывать, где закрывать квест

Ожидаемое поведение:

- квест можно взять через Offer
- после выполнения objectives квест можно закрыть через Reward
- пустой Completion не блокирует Reward

Пример JSON-логики:

```json
"offerTriggerIds": ["hunter_trigger"],
"completionTriggerIds": [],
"rewardTriggerIds": ["hunter_trigger"]
```

---

## 7. Цепочные квесты с Completion

Цепочный квест имеет схему:

```text
Offer -> Completion[] -> Reward
```

Пример:

```text
Взять квест у Ворона.
Выполнить этап у Распутина.
Вернуться к Ворону за наградой.
```

Для такого квеста:

- Offer обязателен
- Completion включён
- должен быть один или несколько Completion-блоков
- Reward обязателен

Ожидаемое поведение:

- квест можно взять через Offer
- каждый Completion-блок должен быть выполнен
- Reward недоступен, пока не выполнены все Completion-блоки
- после выполнения всех Completion-блоков Reward закрывает квест

Пример JSON-логики:

```json
"offerTriggerIds": ["hunter_trigger"],
"completionTriggerIds": ["rasputin_trigger"],
"rewardTriggerIds": ["hunter_trigger"]
```

---

## 8. Изоляция квестов

Каждый `questId` должен обрабатываться отдельно.

Квесты не должны блокировать друг друга автоматически.

Один NPC или trigger может иметь несколько `questIds`.

Порядок `questIds` у trigger:

- может влиять на порядок отображения
- не должен ломать принятие квеста
- не должен ломать сдачу квеста
- не должен создавать скрытую зависимость между квестами

Связь между разными квестами допускается только через:

```text
requiredQuestIds
```

Если квест A должен быть завершён перед квестом B:

```text
это должно быть явно указано в requiredQuestIds квеста B
```

---

## 9. Правила для JSON

В JSON должны быть явно и корректно заполнены:

- `requiredQuestIds`
- `offerTriggerIds`
- `completionTriggerIds`
- `rewardTriggerIds`
- `triggerActions`
- `objectives`
- `rewards`

Правила:

- `requiredQuestIds: []` означает, что внешних зависимостей нет
- `completionTriggerIds: []` означает, что промежуточных Completion-этапов нет
- `rewardTriggerIds` должен быть заполнен всегда
- `offerTriggerIds` должен быть заполнен всегда
- если Completion-этапы есть, они должны быть связаны с текущим `questId`
- если Completion-этапов нет, Reward должен закрывать квест напрямую

---

## 10. Правила для редактора квестов

Редактор должен явно разделять:

- Offer
- Completion
- Reward
- Required completed quests

Русское название для `requiredQuestIds`:

```text
Требуемые завершённые квесты
```

Описание для редактора:

```text
Если список пустой, квест доступен без прохождения других квестов.
Если список заполнен, все указанные квесты должны быть завершены,
иначе этот квест не будет доступен.
```

Completion в редакторе:

- должен быть опциональным
- если Completion выключен, Completion-блоки не создаются
- если Completion включён, должен быть создан один или несколько Completion-блоков
- каждый Completion-блок должен быть связан с текущим `questId`

Reward в редакторе:

- обязателен
- должен быть создан всегда
- если Completion выключен, Reward закрывает квест напрямую
- если Completion включён, Reward закрывает квест только после всех Completion-блоков

---

## 11. Правила для игрового кода

Игровой код должен различать:

```text
Completion отсутствует
```

и

```text
Completion есть, но ещё не выполнен
```

Это разные состояния.

Правильная логика:

Если `completionTriggerIds` пустой:

- Completion отсутствует
- Reward может закрыть квест после выполнения objectives

Если `completionTriggerIds` не пустой:

- Completion есть
- Reward должен проверить, выполнены ли все Completion-этапы

Игровой код не должен считать пустой `completionTriggerIds` ошибкой.

Игровой код не должен блокировать Reward только потому, что `completionTriggerIds` пустой.

## 12. Частичная сдача предметов

Квест может разрешать частичную сдачу предметов через:

```json
"allowPartialTurnIn": 1
```

Если `allowPartialTurnIn` включён:

- игрок может сдавать предметы частями
- прогресс должен сохраняться в данных игрока
- квест не должен завершаться, пока не сданы все необходимые предметы
- после сдачи всех предметов Reward может закрыть квест, если нет невыполненных Completion-этапов

Если предмет использует количество внутри стака, нужно использовать:

```json
"useItemQuantity": 1
```

Если `useItemQuantity` выключен:

```json
"useItemQuantity": 0
```

код считает отдельные предметы, а не количество внутри стака.

Пример:

```text
Carp x6 со useItemQuantity: 0

Один стак Carp quantity=6 будет считаться как 1 предмет.
```

Для стакуемых предметов:

```json
"useItemQuantity": 1
```

---

## 13. Внутреннее количество выдаваемых предметов

Для выдаваемых предметов `quantity` всегда означает количество физических предметов / стаков.

Выдаваемые предметы находятся в:

- `giveItems[]`
- `rewards[]`
- `triggerActions[].rewards[]`

Для каждого выдаваемого item можно указать:

```json
"setItemQuantity": 1,
"itemQuantity": 5
```

Смысл:

- `setItemQuantity = 0` — предмет создаётся как раньше;
- `setItemQuantity = 1` — сервер после создания предмета выставляет ему внутреннее количество;
- `itemQuantity` — внутренняя quantity каждого созданного физического предмета.

Пример:

```text
Ammo_12gaPellets
quantity = 1
setItemQuantity = 1
itemQuantity = 5
```

Ожидаемый результат: один физический стак `Ammo_12gaPellets` с quantity 5.

Если указано `quantity = 2`, `setItemQuantity = 1`, `itemQuantity = 5`, сервер создаёт два физических стака и каждому ставит quantity 5.

Важно не путать:

- objective `useItemQuantity` — как считать и сдавать предметы игрока;
- reward/give item `itemQuantity` — какую внутреннюю quantity поставить создаваемому предмету.

Сервер применяет `itemQuantity` только из server quest config / server profile JSON. Клиентские RPC для accept/complete не передают `className`, `quantity`, `setItemQuantity`, `itemQuantity`, `rewards` или `giveItems`; клиент передаёт только `questId` и `triggerId`.

Если `setItemQuantity = 1`, но созданный предмет не поддерживает quantity или `itemQuantity <= 0`, выдача не должна считаться успешной.

## 14. Статусы квеста

Основные статусы:

- `available` — квест доступен
- `active` — квест взят
- `completed` — квест завершён

Правила:

- Offer переводит квест в `active`
- Reward переводит квест в `completed`
- Completion сам по себе не завершает квест
- Completion только открывает возможность закрыть квест через Reward

---

## 15. UI-правила

UI должен показывать игроку состояние квеста понятно.

Если квест недоступен из-за `requiredQuestIds`:

- квест можно скрыть
- или показать как заблокированный
- желательно объяснить, какие квесты нужно завершить

Если квест active и Completion не выполнен:

- Reward-кнопка должна быть недоступна
- UI должен объяснить, какие промежуточные этапы нужно выполнить

Если квест active и Completion отсутствует:

- Reward не должен блокироваться из-за пустого `completionTriggerIds`
- сдача должна проверяться через objectives и rewardTriggerIds

Если квест active и objectives не выполнены:

- кнопка завершения может быть недоступна
- UI должен показать, какие предметы или условия ещё нужны

---

## 16. Короткое правило

Главное правило:

```text
Offer — взять квест.
Completion — выполнить промежуточные этапы, если они есть.
Reward — закрыть квест и выдать награду.
requiredQuestIds — открыть доступ к квесту только после завершения других квестов.
```

Важно:

- Completion относится к этапам внутри текущего квеста
- `requiredQuestIds` относится к зависимостям между разными квестами
- пустой Completion не блокирует Reward
- пустой `requiredQuestIds` не блокирует доступ к квесту
- квесты не должны случайно переплетаться между собой
- все связи между квестами должны быть явными
- если квест зависит от другого квеста, это должно быть указано в `requiredQuestIds`
