## Цель теста

Проверить, может ли migration-группа, созданная серверным скриптом, физически пройти рассчитанный navmesh-маршрут и продолжить движение после удаления игрока более чем на 500 метров.

## Погодный предвестник и runtime schema

При текущих defaults через `eventDelaySeconds = 30` секунд начинается единый глобальный погодный переход длительностью `weatherTransitionSeconds = 180` секунд. Его цели: overcast `1.0`, fog `0.8`, rain `0.0` и wind `0.0` в JSON; фактически vanilla API использует подтверждённый минимальный wind speed `0.1 m/s`. Оба source scenarios имеют `weatherChangeEnabled = 1`, поэтому обе включённые migration-группы создаются в одном общем моменте только после завершения перехода.

Корневой `weatherEnabled` остаётся master switch. Если он равен `1`, одного `weatherChangeEnabled = 1` среди включённых scenarios достаточно для одного общего transition всей пачки. Если все включённые scenarios имеют `0` либо global switch равен `0`, transition пропускается и группы запускаются после обычного `eventDelaySeconds`. Значение scenario `0` означает только «не инициировать»: погода DayZ глобальна, поэтому смешанная пачка `0 + 1` всё равно целиком находится в изменённом мире.

Гроза включена отдельно от дождя. Первые `120` секунд transition storm density остаётся `0`, затем за последние `weatherStormRampSeconds = 60` секунд повышается server-side шагами по `10` секунд и к spawn достигает `0.8`. `SetStorm()` не имеет transition-параметра, поэтому manager выполняет ограниченную последовательность scheduled updates, а не обновление каждый frame. `weatherRain = 0.0` независимо ведёт rain к нулю.

Существующий `MigrationConfig.json` не переписывается и не пересобирается: пользовательские значения, порядок полей и порядок объектов `scenarios` сохраняются. Отсутствующие поля могут получить constructor defaults только в runtime-объекте, без записи обратно; массив сценариев текстово не патчится. Malformed unified JSON остаётся нетронутым и останавливает запуск события.

Если unified-файла ещё нет, loader может один раз безопасно собрать его из старых `MigrationEvent.json`, `MigrationScenario_001.json` и `MigrationScenario_002.json`. Существующие legacy-файлы обязаны успешно прочитаться; затем новый временный JSON валидируется. Старые runtime-файлы не удаляются и не изменяются. После появления `MigrationConfig.json` активным считается только он, а старые файлы игнорируются.

## Движение по маршруту

Для каждого заражённого маршрут имеет вид:

`spawnPosition -> routePoints[0] -> routePoints[1] -> ... -> targetPosition`

`routePoints` — произвольный массив, не ограниченный фиксированным количеством элементов. При пустом массиве сохраняется прямой маршрут spawn -> target. Для каждого заражённого один раз рассчитывается стабильный индивидуальный formation offset; тот же offset применяется ко всем промежуточным точкам и конечной цели.

На каждом отрезке:

1. `AIWorld::SampleNavmeshPosition()` находит ближайшие доступные стартовую и текущую целевую позиции.
2. `AIWorld::FindPath()` строит массив waypoints.
3. В спокойном состоянии `DayZInfectedInputController::OverrideHeading()` направляет заражённого к следующей точке.
4. `OverrideMovementSpeed()` задаёт физическое движение со скоростью прототипа `1.0`.
5. При достижении waypoint выбирается следующий.
6. При входе в горизонтальный `routePointReachRadius = 6.0` текущая промежуточная точка отмечается пройденной, после чего путь строится к следующей.

Телепортация между точками не используется.

## Волновая активация route points (опциональная)

После TASK 141 standard source default равен `routeActivationEnabled = 0`. Код percentage accumulation, параметры и parser contract не удалены: специальный scenario может явно включить их значением `1`. Если у runtime-группы одновременно отключены route и final activation, manager пропускает её до `CountActiveGroupMembers()`.

Навигационный `routePointReachRadius = 6.0` и group counting radius — разные величины. Первый переключает индивидуальный segment infected; второй по default равен `routeActivationRadius = 12.0` и считает группу вокруг raw route point. `routeActivationRadii[index]` может переопределить радиус отдельной точки, а отсутствующее, короткое или неположительное значение использует общий fallback.

Для каждой runtime-группы denominator равен текущему числу живых, ещё не `RELEASED` members этой группы. Убитые сразу исключаются. Другие vanilla/mod infected и members других runtime groups не считаются. Порог:

`required = ceil(aliveActiveMembers * routeActivationTriggerPercent / 100)`

При наличии живых members минимум равен `1`. Подсчёт выполняется по X/Z без физических trigger entities. Каждая route point имеет собственный ARMED/TRIGGERED state. При `inside >= required` ARMED-точка создаёт один stimulus в raw route point и disarm. Пока условие остаётся истинным, повторного spam-trigger нет. При `inside < required` точка rearmed, и новый рост до threshold создаёт следующий импульс. Обязательного waiting timer нет.

Один стабильный formation offset продолжает использоваться только для navigation targets (`raw point + offset`). Counting zone и stimulus всегда центрируются по общей raw route point.

## Финальная accumulation zone (опциональная) и final hold

При явном `finalActivationEnabled = 1` `targetPosition` работает как аналогичная group accumulation zone. Denominator остаётся числом живых active members конкретного spawn instance, а inside-счётчик определяется только их фактическим положением в горизонтальном `finalActivationDistance = 12.0`, независимо от логического индекса маршрута. Порог `finalActivationTriggerPercent` по умолчанию остаётся `30.0`, но standard source default самого переключателя после TASK 141 равен `0`.

При threshold создаётся один stimulus точно в raw `targetPosition`. Final zone тоже rearmed после падения occupancy ниже текущего порога и может выдать новый импульс при повторном накоплении. Этот stimulus не переводит группу или вошедших в радиус infected в `RELEASED`.

TASK 139 меняет итоговое поведение actual arrival. Если `finalHoldEnabled = 0`, сохраняется старый терминальный вариант: конкретный infected получает `RELEASED`, исключается из дальнейшего route control и остаётся vanilla AI.

Если `finalHoldEnabled = 1`, actual arrival переводит конкретного infected в `HOLD_FREE`, а не в терминальный `RELEASED`. Manager снимает `OverrideHeading` / `OverrideMovementSpeed`, очищает path и оставляет infected свободно жить под vanilla AI внутри `finalHoldRadius = 200.0` метров от raw `targetPosition`.

Если `HOLD_FREE` infected индивидуально вышел за `finalHoldRadius`, manager не возвращает его силой во время vanilla aggro. Только после `target == null`, `CALM` и защитного cooldown запускается `RETURN_TO_HOLD`: путь строится к индивидуальной финальной цели `targetPosition + routeOffset`. При входе в `finalHoldReturnRadius = 30.0` infected снова становится `HOLD_FREE`.

Локально подтверждённый API: `NoiseSystem::AddNoiseTarget(vector pos, float lifetime, NoiseParams params, float multiplier)` из `P:\scripts\3_game\noise.c`. Параметры загружаются через `NoiseParams.LoadFromPath("CfgVehicles SurvivorBase NoiseShout")`; существование этого preset подтверждено в `P:\DZ\characters\data\config.cpp`. Аналогичный вызов `AddNoiseTarget()` из произвольной мировой позиции показан в `P:\scripts\4_world\static\miscgameplayfunctions.c`.

Stimulus является AI-only: мод не создаёт слышимый игроку `SoundSet`/`SoundObject` и не пытается принудительно установить `CHASE`, `FIGHT` или иной native mind state. Поэтому реальная сила реакции, радиус восприятия и способность улучшить прохождение препятствий пока не считаются runtime-доказанными. Другие infected рядом не входят в percentage, но могут естественно воспринять этот же world stimulus.

Default route/final lifetime равен `1.0` секунде, strength multiplier — `1.0`. Если noise preset или `NoiseSystem` недоступны, counting, маршрут и итоговое arrival-поведение продолжают работать без AI stimulus. При отключённой route или final activation соответствующие group stimuli не создаются.

`RELEASED` остаётся терминальным состоянием manager только для режима, где `finalHoldEnabled = 0`: entity не удаляется, `ECE_NOLIFETIME` не добавляется, новые пути и retries больше не назначаются, а дальнейшее поведение полностью остаётся vanilla AI.

## Направленное восстановление застрявших infected

TASK 139 добавляет индивидуальный stuck detection для `MIGRATION` и `RETURN_TO_HOLD`. Он не применяется к `HOLD_FREE`, dead infected, терминальному `RELEASED` и любому active vanilla AI.

По default каждые `stuckDetectionSeconds = 6.0` секунд infected сравнивает текущую world position с собственным sample только в горизонтальной плоскости X/Z. Если итоговое смещение меньше `stuckMinMovementMeters = 2.0`, пишется `STUCK_DETECTED`; ровно `2.0` считается достаточным движением и начинает новый sample interval. Progress к nav waypoint/route target допускается только как диагностическое значение и не отменяет stuck.

При recovery manager:

- снимает migration overrides;
- переводит infected в `STUCK_RECOVERY`;
- создаёт AI-only stimulus примерно на `stuckStimulusForwardDistance = 10.0` метров впереди по горизонтальному направлению к waypoint/route target;
- даёт минимум `stuckRecoveryFreeSeconds = 30.0` секунд vanilla freedom.

Recovery stimulus работает строго индивидуально. Только infected, который сам получил `STUCK_DETECTED` или `ROUTE_PROGRESS_LOST`, переводится в `STUCK_RECOVERY` и создаёт один собственный directed stimulus. Nearby infected могут естественно услышать world AI stimulus, но manager не меняет их recovery state. Чужой недавний stimulus не блокирует собственный импульс следующего infected.

Пока infected находится в `STUCK_RECOVERY`, оба detector не выполняются, поэтому один incident создаёт не более одного stimulus. После resume и нового `BuildPath()` samples создаются заново, и при следующем реальном stuck тот же infected снова может выполнить полный recovery cycle. `stuckStimulusShareRadius` и `stuckStimulusRetrySeconds` остаются legacy JSON/parser fields для backward compatibility, но manager больше их не использует.

После free-period manager проверяет состояние не чаще `stuckRecoveryStatusCheckSeconds = 3.0`. Пока есть target или mind state не `CALM`, возврат к маршруту не выполняется. После `target == null`, `CALM` и cooldown путь строится заново от текущей позиции к сохранённому intent: `MIGRATION` или `RETURN_TO_HOLD`.

## Route Progress Watchdog

Второй индивидуальный detector дополняет короткий stuck TASK 141 и ловит infected, который физически смещается, но не приближается к своей текущей логической цели. Watchdog работает только в `MIGRATION` и `RETURN_TO_HOLD`; target берётся через `GetCurrentRouteTarget(state)`, а не из текущего navmesh waypoint.

Source defaults: enabled `1`, comparison window `30 sec`, полезный progress минимум `5 m`, immediate backtrack `10 m`, предел плохих окон `2`. Уход назад на `>= 10 m` даёт `ROUTE_PROGRESS_LOST / BACKTRACK` сразу. Меньше `5 m` полезного прогресса увеличивает индивидуальный counter; два таких окна подряд дают `ROUTE_PROGRESS_LOST / NO_PROGRESS`.

Первый baseline разных infected распределяется controlled jitter по времени. Обычный check использует только world position и X/Z distance, не вызывает `FindPath()` и не сканирует группу. После подтверждения проблемы переиспользуется существующий directed recovery к logical target с vanilla freedom, `CALM`/cooldown и последующим `BuildPath()`. В `AGGRO`, `STUCK_RECOVERY`, `HOLD_FREE` и `RELEASED` watchdog приостановлен и его baseline сброшен.

## Vanilla aggro и возврат

Manager не заменяет зрение, слух, target selection, `CHASE` или `FIGHT`.

Если `GetTargetEntity()` возвращает цель либо `GetMindState()` отличается от `CALM`, manager:

- снимает `OverrideHeading` и `OverrideMovementSpeed`;
- устанавливает наблюдаемый режим `AGGRO`;
- оставляет управление vanilla AI.

Возврат к маршруту разрешается только после одновременного выполнения условий:

- `GetTargetEntity() == null`;
- mind state равен `CALM`;
- прошёл защитный cooldown `5` секунд.

Затем путь пересчитывается от фактической текущей позиции к текущей непройденной `routePoint` либо к индивидуальной конечной цели, и режим снова становится `MIGRATION`. Если aggro произошёл во время `RETURN_TO_HOLD`, после `target == null`, `CALM` и cooldown возвращается именно `RETURN_TO_HOLD`, а не старый маршрут сначала. Это же применяется после временного vanilla disturbance от group stimulus или stuck recovery.

В `HOLD_FREE` manager не назначает route control внутри `finalHoldRadius`. Если infected вышел за radius, возврат к поселению всё равно начинается только после проверки vanilla AI: target отсутствует, mind state `CALM`, затем cooldown. После терминального `RELEASED` возврат к migration-маршруту запрещён.

## Серверный лог

Source defaults: `loggingEnabled = 1`, `stuckDebugLoggingEnabled = 0`. Для целевого теста TASK 146 пользователь вручную ставит оба значения в `1` в существующем `$profile:Silver_77_Migrate/MigrationConfig.json`; runtime-файл автоматически не меняется.

При включённом INFO каждая строка с server-runtime `timeMs` пишется одновременно через `Print()` в RPT и в:

`$profile:Silver_77_Migrate/Migration.log`

File handle открывается один раз на server session в append-режиме и закрывается при штатном `Stop()`. `SESSION_START` и `SESSION_END` отделяют сессии. ERROR остаётся в RPT независимо от `loggingEnabled` и дублируется в profile log, если файл доступен.

Общие погодные сообщения используют префикс `[S77Migrate][EVENT]`. Все важные сообщения конкретной группы содержат стабильные поля `scenario=`, `group=`, `id=` и `mode=` там, где они применимы.

Для каждого созданного заражённого с интервалом `logIntervalSeconds` выводятся:

- scenario ID;
- внутренний infected ID;
- class name;
- текущая позиция;
- индекс и количество промежуточных `routePoints`;
- индекс и количество waypoints;
- горизонтальное расстояние до центра `targetPosition`;
- наличие vanilla target: `YES` или `NO`;
- mind state;
- режим `MIGRATION`, `AGGRO`, `STUCK_RECOVERY`, `HOLD_FREE`, `RETURN_TO_HOLD` или `RELEASED`.

При `stuckDebugLoggingEnabled = 1` цепочка короткого detector содержит `STUCK_SAMPLE_START`, через полный interval — `STUCK_SAMPLE_CHECK` с `positionA`, `positionB`, `elapsedSeconds`, `movedXZ`, threshold и `result=MOVING/STUCK`. Если sample прерван, `STUCK_SAMPLE_RESET reason=...` показывает lifecycle-причину. Эти debug markers не создаются каждый manager tick.

Важный recovery incident журналируется последовательностью `STUCK_DETECTED` либо `ROUTE_PROGRESS_LOST`, `STUCK_RECOVERY_RELEASE`, `STUCK_RECOVERY_STIMULUS_ATTEMPT`, затем ровно одним `STUCK_RECOVERY_STIMULUS_OK`, `..._FAILED` или `..._SKIPPED`, после чего ожидаются `STUCK_RECOVERY_CALM` и `STUCK_RECOVERY_RESUME`. Результат `OK/FAILED` использует фактический bool `EmitAIStimulus()`; `cause=STUCK` и `cause=ROUTE_PROGRESS_LOST` различаются.

Также журналируются runtime group start, spawn, `BUILD_PATH`, `PATH_ERROR`, `ROUTE_POINT_REACHED`, route/final activation, vanilla aggro handoff/resume, arrival, `HOLD_FREE`, `RETURN_TO_HOLD`, `RELEASED` и `DEATH`. Сложная rotation/size limit для одного append-файла остаётся будущей задачей; основная текущая защита — `stuckDebugLoggingEnabled = 0` вне диагностики.

## Как запустить тест

Только после отдельной сборки и установки server-only мода:

1. Запустить сервер с `-serverMod=@Silver_77_Migrate_server`, чтобы появился единый runtime-конфиг, либо заранее подготовить его по source-образцу.
2. Проверить глобальные настройки event/weather и оба объекта массива `scenarios`: `enabled`, координаты, `routePoints`, количество, formation, route/final activation, stuck recovery и final hold.
3. При необходимости остановить сервер и вручную изменить пользовательские значения `MigrationConfig.json`.
4. Запустить сервер с модом для теста последовательности `30 секунд -> 180 секунд weather transition -> одновременный spawn Scenario 001 и 002`.

За один запуск сервера общее событие и каждая включённая группа стартуют не более одного раза. Для повторного чистого теста нужен перезапуск сервера.

## Процедура ручной проверки

1. Подойти к району стартовой точки.
2. Убедиться, что система создала настроенное количество заражённых; при текущем default это десять ID `INF_1`–`INF_10`.
3. Подтвердить последовательное прохождение новых `routePoints` по сообщениям `ROUTE_POINT`.
4. Спровоцировать одного заражённого и подтвердить в журнале `target=YES` или боевой mind state вместе с `mode=AGGRO`.
5. Уйти от заражённого, дождаться потери target, состояния `CALM`, cooldown и нового сообщения о построенном пути.
6. Подтвердить возвращение режима `MIGRATION` и продолжение движения к текущей непройденной точке.
7. Удалиться от группы более чем на 500 метров.
8. Через журнал проверить, менялись ли координаты заражённых без игрока рядом.
9. Вернуться к маршруту или конечной точке и сверить фактическое положение с журналом.
10. При standard `routeActivationEnabled = 0` убедиться, что `ROUTE_ACTIVATION` отсутствует.
11. При standard `finalActivationEnabled = 0` убедиться, что `FINAL_ACTIVATION` отсутствует, а natural vanilla aggression продолжает работать.
12. Опциональную percentage accumulation проверять отдельным запуском только после явного включения соответствующего переключателя.
13. Сымитировать stuck у одного infected на дереве/заборе и проверить индивидуальный `STUCK_DETECTED` примерно через `6` секунд, если его итоговое X/Z-смещение меньше `2` метров и active vanilla target отсутствует.
14. Подтвердить, что перед recovery stimulus снимаются migration overrides, а собственный stimulus infected появляется примерно на `10` метров впереди по прежнему направлению движения.
15. Подтвердить минимум около `30` секунд vanilla freedom после stuck recovery.
16. Во время recovery спровоцировать игроком aggro и убедиться, что manager не перебивает погоню.
17. После `target=NO`, `CALM` и cooldown подтвердить `STUCK_RECOVERY_RESUME` и новый path от текущей позиции к правильному intent.
18. При `finalHoldEnabled=1` подтвердить, что actual arrival даёт `HOLD_ENTER` / `HOLD_FREE`, а не терминальный `RELEASED`.
19. Внутри `finalHoldRadius = 200.0` убедиться, что infected свободно живёт vanilla AI и manager не тянет его в центр.
20. Увести/спровоцировать одного `HOLD_FREE` infected за `finalHoldRadius` и подтвердить, что активная vanilla aggro не перебивается.
21. После `target=NO`, `CALM` и cooldown подтвердить индивидуальный `HOLD_RETURN_START`.
22. На `RETURN_TO_HOLD` подтвердить обычный path control и stuck recovery.
23. После входа в `finalHoldReturnRadius = 30.0` подтвердить `HOLD_RETURNED` и возврат в `HOLD_FREE`.
24. Отдельно проверить независимое отключение `routeActivationEnabled`, `finalActivationEnabled`, `stuckRecoveryEnabled` и `finalHoldEnabled`.
25. Для физически движущегося infected подтвердить immediate `ROUTE_PROGRESS_LOST reason=BACKTRACK` при увеличении distance минимум на `10 m` за окно.
26. Подтвердить, что одно слабое окно не запускает recovery, а два подряд дают `ROUTE_PROGRESS_LOST reason=NO_PROGRESS`.
27. Проверить отсутствие watchdog-trigger в `AGGRO`, `STUCK_RECOVERY` и `HOLD_FREE`, его работу в `RETURN_TO_HOLD`, а также отсутствие массового `FindPath()` на обычных проверках.
28. Поставить рядом минимум двух stuck infected: первый собственный stimulus не должен автоматически переводить второго в `STUCK_RECOVERY`.
29. Если второй infected остался неподвижным, подтвердить его собственные `STUCK_DETECTED` и `STUCK_RECOVERY_STIMULUS`; nearby stimulus первого не должен подавлять второй.
30. После resume снова застрять тем же infected и подтвердить новый отдельный recovery cycle; также проверить own stimulus после `ROUTE_PROGRESS_LOST`.
31. Вручную добавить в верхний уровень runtime JSON `"loggingEnabled": 1` и `"stuckDebugLoggingEnabled": 1`, не меняя scenario-поля TASK 141/142.
32. Убедиться, что появился `$profile:Silver_77_Migrate/Migration.log`, а те же важные строки присутствуют в RPT.
33. Для одного `id=` проследить `STUCK_SAMPLE_START -> STUCK_SAMPLE_CHECK`; сверить A/B, elapsed, `movedXZ` и `MOVING/STUCK`.
34. Для результата `STUCK` получить `STUCK_DETECTED -> STUCK_RECOVERY_RELEASE -> STUCK_RECOVERY_STIMULUS_ATTEMPT` и ровно один итог `OK`, `FAILED` или `SKIPPED`, затем CALM/resume либо gated WAIT_BUSY.
35. Выключить `stuckDebugLoggingEnabled`: sample markers должны исчезнуть, а важные recovery events сохраниться. Затем выключить `loggingEnabled` и подтвердить отсутствие INFO при сохранении ERROR в RPT.
36. При `weatherEnabled=1` и `weatherChangeEnabled=0` у всех enabled scenarios подтвердить `WEATHER_DECISION ... result=SKIP_NO_SCENARIO_REQUEST`, отсутствие transition и старт групп после `eventDelaySeconds`.
37. При `weatherEnabled=1` и хотя бы одном `weatherChangeEnabled=1` подтвердить ровно один `WEATHER_DECISION ... result=TRANSITION`, один weather transition и один запуск всей пачки.
38. При `weatherEnabled=0` и scenario flag `1` подтвердить `result=SKIP_GLOBAL_DISABLED` и отсутствие transition.
39. В смешанной пачке `0 + 1` подтвердить один global transition: scenario с `0` его не инициирует, но находится в общей изменённой погоде.

## Критерии результата

Тест считается успешным только если runtime подтверждает всё перечисленное:

- создано настроенное количество наших заражённых; текущий default — `10`;
- они последовательно и независимо проходят произвольный массив `routePoints` и navmesh waypoints без телепортации;
- координаты продолжают изменяться после удаления игрока более чем на 500 метров;
- aggro передаёт движение vanilla AI;
- после потери target и cooldown маршрут пересчитывается к текущей непройденной точке;
- при standard route/final activation `0` отсутствуют percentage-triggered group stimuli и natural aggro остаётся рабочим;
- при отдельном явном включении опциональной legacy-механики ARMED/TRIGGERED/rearm по-прежнему не создаёт spam и допускает новый pulse после реального падения/роста occupancy;
- после vanilla disturbance и `CALM` active infected продолжает migration;
- индивидуальный stuck определяется по итоговому X/Z world displacement `< 2 m` за `6 sec`, не зависит от progress к waypoint или процента группы, а recovery не создаёт log/stimulus spam и не перебивает active vanilla AI;
- каждый подтверждённый incident конкретного infected создаёт его собственный directed stimulus без forced recovery соседей и spatial suppression; после resume новый incident снова разрешён;
- Route Progress Watchdog использует logical route target, независимо обнаруживает `BACKTRACK` и два последовательных `NO_PROGRESS`, распределяет проверки по времени и не вызывает `FindPath()` без подтверждённой проблемы;
- при `finalHoldEnabled=1` actual arrival переводит конкретного infected в `HOLD_FREE`, а индивидуальный `RETURN_TO_HOLD` включается только после выхода за hold radius, `target=NO`, `CALM` и cooldown;
- при `finalHoldEnabled=0` сохраняется старый terminal arrival -> `RELEASED`.
- корневой weather master switch и scenario-level requests дают один ожидаемый batch transition либо корректный skip без двойного `StartAllScenarios()`.

Если движение прекращается вдали от игроков, это отдельный подтверждённый результат эксперимента, а не основание скрывать или придумывать успех. Ошибки `PATH ERROR`, отсутствие нужного aggro handoff или невозможность вернуться к маршруту также фиксируются отдельно.

## Ограничения прототипа

Прототип не содержит интеграцию с Quest Server, quest JSON, UI, RPC, клиентский мод, расписание, случайные события, persistence, database, админ-панель или изменения Central Economy. Он управляет заражёнными включённых объектов массива `scenarios`, запущенных одним глобальным событием; текущий default содержит два тестовых сценария.
