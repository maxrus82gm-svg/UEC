# QUEST UI RULES

Правила для задач по `QuestMenu`, `QuestJournal` и пользовательскому поведению квестового UI.

## 1. Что сюда относится

Читать для задач по:

- `QuestMenu`
- `QuestJournal`
- `QuestUI.c`
- квестовым `.layout`
- текстам кнопок и панелей
- отображению Offer / Completion / Reward

## 2. Смысл панелей

`DescriptionPanel / DescriptionText`:

- описание квеста;
- смысл задачи;
- цели;
- прогресс;
- что нужно принести;
- что уже сдано;
- награды;
- требования;
- статус квеста.

`DialogPanel / DialogText`:

- что говорит NPC;
- текст текущего action-блока;
- `triggerActions[].dialogText`;
- контекст разговора `Offer / Completion / Reward`.

Нельзя использовать `triggerActions[].dialogText` как основное описание квеста в `DescriptionPanel`.

## 3. Route и список квестов

`RoutePanel` и связанные метки должны показывать маршрут / контекст действия и не должны подменять собой описание квеста.

В левом списке не нужно без отдельной задачи возвращать лишние префиксы и лишний визуальный шум, если он уже был удалён.

## 4. Префиксы, prompt и визуальный шум

1. Не возвращать лишний `[F]` в квестовый UI без отдельной задачи.
2. Не считать `action prompt` частью layout-проблемы автоматически.
3. Если `action prompt` мешает интерфейсу, это отдельная UI-задача.
4. Не менять фон, плотность overlay и общий визуальный баланс без явной задачи.

## 5. Scroll и длинные тексты

Если длинные тексты обрезаются:

- сначала подтвердить, что проблема действительно в прокрутке/контейнере;
- потом делать отдельную задачу на `scroll`;
- не смешивать её с правками RPC, JSON и server progress.

## 6. UI и данные надо проверять вместе

`QuestMenu.layout` и `QuestUI.c` нужно проверять вместе.

Если проблема:

- в размере / позиции / фоне -> это чаще `layout`;
- в тексте / префиксах / маппинге `Description` vs `Dialog` -> это чаще `QuestUI.c`;
- в статусах / кнопках / доступности -> сначала проверять данные и sync;
- в прогрессе / сохранении -> это чаще server-side данные.

## 7. Не считать UI первопричиной без проверки sync

Пока не подтверждено, что серверные данные дошли до клиента и применились:

- не считать UI первопричиной;
- не начинать с кнопок;
- не начинать с layout;
- сначала сверяться с `DAYZ_RPC_SYNC_RULES.md`.

## 8. Ручная проверка после UI-правок

После значимых UI-изменений обязательно проверять в игре:

1. `Offer NPC`
2. `Completion NPC`
3. `Reward NPC`
4. `QuestJournal`
5. кнопки
6. кириллицу
7. длинные тексты
8. общий визуальный комфорт

## 9. Связанные документы

Для структуры данных читать:

- `Documentation/SplitDoc/QUEST_JSON_CONTRACT.md`

Для кириллицы и `.layout`:

- `Documentation/SplitDoc/ENCODING_RULES.md`

Для viewer-задач:

- `Documentation/SplitDoc/DAYZ_LAYOUT_VIEWER_RULES.md`

## 10. Совместимость с DayZ_layout viewer

Если задача меняет `QuestMenu`, `QuestJournal`, `.layout`, `UIScriptedMenu`, `widget classes`, `styles`, `scroll`-паттерны или структуру UI, агент обязан сразу учитывать совместимость с `DayZ_layout viewer`.

Это означает:

- проверить, сможет ли `DayZ_layout viewer` корректно показать новые или изменённые UI-элементы;
- проверить, понимает ли viewer новые `widget classes`, `styles`, контейнеры, scroll-паттерны и изменения структуры меню;
- если viewer не поддерживает новый элемент или показывает его некорректно, не исправлять viewer вне scope, а явно указать это в `PROBLEMS`;
- если viewer отстал от актуального UI, предложить отдельную задачу на обновление `DayZ_layout`;
- обновлять viewer вместе с UI только если текущая задача прямо разрешает менять viewer.
