# ENCODING RULES

Операционные правила по кодировкам и кириллице для задач агента.

## 1. Главный принцип

Русский текст нельзя повреждать.

Предпочтительный формат для новых и уже нормализованных файлов проекта:

- `UTF-8` без BOM

Но не считать, что все существующие файлы уже находятся в `UTF-8`.

## 2. Когда нужен этот документ

Читать для задач, связанных с:

- `QuestMenu`, `QuestJournal`, `QuestUI`;
- `.layout`, `.json`, `.md`, `.txt`, `.xml`, `.c`, `.cpp`;
- кириллицей в UI, документации и конфигурации;
- диагностикой сломанного русского текста.

## 3. Базовые правила

1. Не перекодировать файлы без отдельной задачи.
2. Не сохранять файл заново, если задача только аналитическая.
3. Не заменять кириллицу на `????`, кракозябры или транслит.
4. Не чинить русские строки автоматически без подтверждения смысла и кодировки.
5. Перед изменением файла с кириллицей определить его текущую кодировку.
6. Если кодировка непонятна, остановиться и указать риск в отчёте.
7. Не менять кавычки, переносы строк и спецсимволы в JSON без задачи.
8. Не форматировать JSON или Markdown целиком, если задача касается одного блока.
9. Не делать массовую перекодировку нескольких файлов без отдельной прямой команды.

## 4. Практика по проекту

Некоторые файлы проекта могут быть в `CP1251` или другой Windows-кодировке.

Особенно осторожно работать с:

- `Silver_77_Quests_Client/gui/QuestMenu.layout`
- `Silver_77_Quests_Client/gui/QuestJournal.layout`
- `JSON_Quvest/*.json`
- `Documentation/*.md`

Если текст выглядит как `�����` или `Р’С‹...`, это ещё не доказывает порчу файла:

1. сначала проверить способ чтения;
2. затем проверить фактическую кодировку;
3. только потом решать, нужна ли правка.

При чтении JSON/текстовых файлов с кириллицей из PowerShell всегда указывать кодировку явно:

- читать через `Get-Content -Encoding UTF8`;
- писать через `[System.Text.UTF8Encoding]::new($false)`, если файл должен быть `UTF-8` без BOM;
- не считать файл испорченным, если на диске он корректный, но сервер или скрипт вернул `РќР°...` из-за чтения без `-Encoding UTF8`.

## 5. Правила патчей и якорей при кириллице

Для файлов с кириллицей основной patch anchor должен быть ASCII-техническим, а не русским пользовательским текстом.

Предпочтительные якоря:

- имена функций;
- имена переменных;
- JSON-ключи;
- HTML `id`;
- `data-action`, `data-path` и другие `data-*` атрибуты;
- CSS/class имена;
- технические константы;
- endpoints и API paths;
- другие стабильные ASCII-фрагменты рядом с нужным местом.

Русские строки можно менять, если задача этого требует, но место правки нужно искать через ближайший стабильный ASCII-якорь.

Если патч по русской строке не совпал:

1. не делать широкий общий патч;
2. не захватывать большую функцию или соседнюю логику вслепую;
3. сначала найти ближайший ASCII-якорь;
4. менять минимальный участок.

Кривое отображение кириллицы в PowerShell или терминале не считать доказательством порчи файла. Перед выводом о проблеме нужно проверить способ чтения и фактическую кодировку.

После правки выполнять доступные проверки, подходящие типу файла:

- `node --check` для JS;
- PowerShell AST parse для `.ps1`;
- `ConvertFrom-Json` для JSON;
- `git diff --check`;
- другую локальную проверку, если она лучше подходит файлу.

## 6. Правила для layout и UI

1. При работе с `.layout` не менять стили, размеры, anchors и visibility без отдельной задачи.
2. Не пересохранять `.layout` ради эксперимента с кодировкой.
3. Если задача касается только viewer-а, не пытаться "чинить" исходный `.layout`.
4. При смене способа чтения нужно исходить из исходных bytes, а не из уже испорченной строки.

## 7. Что писать в отчёте

Если задача затрагивает файл с кириллицей, агент обязан указать:

- была ли обнаружена кириллица;
- отображается ли она нормально;
- есть ли риск кодировки;
- менялся ли файл;
- сохранялся ли файл заново.

## 8. Связанные документы и риск дублей

В проекте уже существует внешний документ:

- `Documentation/RUSSIAN_ENCODING.md`

Этот `SplitDoc` предназначен как короткий агентский набор рабочих правил.

`Documentation/RUSSIAN_ENCODING.md` не меняется в этой миграции и остаётся отдельным расширенным справочным документом. Если между ними появится расхождение, это нужно считать риском нескольких источников правды и отдельно выносить в задачу на синхронизацию.
