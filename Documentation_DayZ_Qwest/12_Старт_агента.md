# СТАРТ АГЕНТА

Короткий агентский свод правил для повседневной работы с `AGENT_TASK_LOOP.md` и `SplitDoc`.

## 1. Что читать всегда

Перед любой задачей читать:

- `Documentation_DayZ_Qwest/11_Задача_агенту.md`
- `Documentation_DayZ_Qwest/12_Старт_агента.md`

Дополнительные `SplitDoc` читать по матрице из `Documentation_DayZ_Qwest/11_Задача_агенту.md`.

## 1.1. Выборочное чтение SplitDoc

ChatGPT является маршрутизатором чтения правил.

Перед подготовкой `БЛОКА 1` ChatGPT должен:

1. определить тему задачи;
2. выбрать минимальный набор тематических `SplitDoc` по матрице;
3. указать эти документы в разделе `Читать`;
4. не указывать все `SplitDoc` подряд без необходимости;
5. не копировать постоянные правила внутрь `БЛОКА 1`, если достаточно ссылки на `START.md` или профильный `SplitDoc`.

Агент читает только:

- `Documentation_DayZ_Qwest/11_Задача_агенту.md`;
- `Documentation_DayZ_Qwest/12_Старт_агента.md`;
- тематические документы из `Documentation_DayZ_Qwest/20_SplitDoc`, прямо указанные в текущем `БЛОКЕ 1`;
- проектные документы из `Documentation_DayZ_Qwest/21_Project_Docs`, прямо указанные в текущем `БЛОКЕ 1`.

Агент не читает все `SplitDoc` подряд на всякий случай.

## 1.2. Обязательный набор правил для квестов

Если задача создаёт или меняет квесты, quest JSON, trigger-связи квеста, награды, objectives, NPC-роли Offer / Completion / Reward или порядок квестов у NPC, перед работой нужно читать весь quest-набор:

- `Documentation_DayZ_Qwest/20_SplitDoc/QUEST_JSON_CONTRACT.md`
- `Documentation_DayZ_Qwest/20_SplitDoc/TRIGGER_RULES.md`
- `Documentation_DayZ_Qwest/20_SplitDoc/QUEST_EDITOR_RULES.md`
- `Documentation_DayZ_Qwest/20_SplitDoc/QUEST_UI_RULES.md`
- `Documentation_DayZ_Qwest/20_SplitDoc/SERVER_PROFILE_RULES.md`

Если задача затрагивает только документацию по квестам, достаточно читать `QUEST_JSON_CONTRACT.md`, `TRIGGER_RULES.md` и сам документ, который меняется.

## 1.3. Обязательный пресет для генерации сюжетных картинок

Если задача связана с генерацией сюжетной картинки, иллюстрации по ЛОРу, визуальной сцены, промпта для изображения или продолжением серии картинок, перед формированием сцены нужно читать:

- `Documentation_DayZ_Qwest/20_SplitDoc/IMAGE_GENERATION_PRESET.md`
- `Documentation_DayZ_Qwest/20_SplitDoc/IMAGE_SCENE_CONTINUITY.md`

Эти документы задают общий визуальный стиль, ограничения, атмосферу, порядок подготовки промпта и постоянные визуальные образы серии.

Не генерировать картинку только по памяти, если доступен ЛОР или профильный документ с пресетом.

## 2. Роли и цикл работы

Пользователь:

- принимает финальные решения;
- проверяет результат в игре и на сервере;
- контролирует Git;
- может вручную обновлять `AGENT_TASK_LOOP.md` и `SplitDoc`.

ChatGPT:

- формирует безопасные задачи;
- даёт полный `БЛОК 1`;
- даёт `REVIEW` и следующую задачу;
- помогает выделять новые постоянные правила.

Агент:

- читает только текущую задачу из `БЛОКА 1`;
- выполняет только текущую задачу;
- возвращает отчёт в чат;
- не делает архитектурных изменений без прямого указания.

## 3. Базовые правила агента

### 3.1. Обязательное правило кодировки

Если задача меняет `.md`, `.json`, `.txt`, `.xml`, `.layout`, `.c`, `.cpp` или любой файл с кириллицей, агент обязан перед правкой прочитать:

`Documentation_DayZ_Qwest/20_SplitDoc/ENCODING_RULES.md`

Это правило обязательно даже если `ENCODING_RULES.md` не был отдельно указан в тематической матрице.

Русский текст нельзя повреждать.  
Запрещено заменять кириллицу на повторяющиеся знаки вопроса, кракозябры или транслит.

Все новые и нормализованные Markdown/JSON-документы сохранять в `UTF-8` без BOM.

Если используется PowerShell:

- читать через `Get-Content -Encoding UTF8`;
    
- писать через `[System.Text.UTF8Encoding]::new($false)`;
    
- не использовать `Set-Content` / `Out-File` без явного указания UTF-8.
    

Если используется Python:

- читать и писать через `encoding="utf-8"`.
    

Если после чтения текст выглядит повреждённым, агент обязан остановиться и указать риск в отчёте, а не перезаписывать файл.

Если задача затрагивает восстановление русского текста, проблемы кодировки, кракозябры или повреждённую кириллицу, обязательно читать `ENCODING_RULES.md`.

Если в процессе работы кириллица восстанавливалась, это обязательно фиксируется в отчёте: файл, причина, способ восстановления, источник корректного текста и проверки UTF-8 / BOM / повреждённых символов.

### 3.2. Активная задача и очистка БЛОКА 1

Активная задача находится только в `БЛОКЕ 1` файла:

`Documentation_DayZ_Qwest/11_Задача_агенту.md`

Агент выполняет только текущую задачу из активного `БЛОКА 1`.

После успешного выполнения задачи агент обязан очистить активный `БЛОК 1` строго по этому каноническому алгоритму.

Очищается только содержимое завершённой TASK между существующим заголовком:

`# БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА`

и следующим служебным разделителем перед:

`# 🟩 БЛОК 2 — ПОСЛЕДНИЙ ОТЧЁТ АГЕНТА`

Существующий заголовок `# БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА` нельзя удалять, создавать повторно или переносить.

После очистки непосредственно под уже существующим заголовком должны остаться ровно три смысловые строки:

Активной задачи нет.
Предыдущая задача выполнена.
Ожидается новая задача от пользователя.

После них сохраняется существующий разделитель и начинается `БЛОК 2`.

Эталон итоговой структуры:

# БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

Активной задачи нет.
Предыдущая задача выполнена.
Ожидается новая задача от пользователя.

================================================================================

# 🟩 БЛОК 2 — ПОСЛЕДНИЙ ОТЧЁТ АГЕНТА

Важно: этот пример показывает итоговую структуру документа. Его нельзя целиком вставлять внутрь уже существующего `БЛОКА 1`, иначе появится duplicate heading.

После очистки агент обязан выполнить self-check:

1. Заголовок `# БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА` в активной рабочей части файла существует ровно один раз.
2. Номер и текст завершённой TASK внутри `БЛОКА 1` отсутствуют.
3. Под заголовком находятся три стандартные строки заглушки.
4. `БЛОК 2 — ПОСЛЕДНИЙ ОТЧЁТ АГЕНТА` не удалён и не перемещён.
5. Разделитель между `БЛОКОМ 1` и `БЛОКОМ 2` сохранён.
6. `БЛОК 2` содержит отчёт завершённой задачи.
7. Если TASK завершилась со статусом `BLOCKED` или не выполнена, `БЛОК 1` автоматически не очищать.

Выполненные задачи не должны оставаться в активном `БЛОКЕ 1`.

### 3.3. Границы задачи

1. Не выполнять задачи из истории, review или подсказок как активные, если они не перенесены в `БЛОК 1`.
    
2. Если задача аналитическая, ничего не менять.
    
3. Если задача требует правки, менять только явно разрешённые файлы.
    
4. Не выходить за пределы указанных файлов молча. Если нужен другой файл, сначала указать это в отчёте.
    
5. Не менять архитектуру, структуру каталогов и контракт данных без отдельной задачи.
    
6. Не удалять, не переносить и не переименовывать файлы без отдельного разрешения.
    
7. Не трогать JSON квестов, реальные серверные пути и runtime-данные без прямой команды.
    
8. При сомнениях сначала делать диагностику и коротко фиксировать риск, а не расширять объём правок.
    
9. Если задача диагностическая, не чинить несколько уровней системы одновременно.
    
10. Если менялись только JSON, документация или локальный редактор `JSON_Quvest`, в отчёте обязательно писать: “моды обновлять не нужно”.

### 3.4. Уточнения после постановки задачи

Если активная задача уже поставлена в `БЛОК 1`, а `AGENT REPORT` по ней ещё не получен, ChatGPT не должен переписывать `БЛОК 1` из-за мелких дополнительных уточнений пользователя.

Все дополнительные мысли, ограничения, пояснения и корректировки, появившиеся до получения `AGENT REPORT`, передаются агенту отдельным коротким сообщением в чат.

Короткое сообщение агенту должно обязательно содержать:

- путь к файлу с активной задачей;
- указание, что задача находится в `БЛОКЕ 1`;
- номер или название текущей задачи;
- краткое описание нового уточнения;
- явное указание, менять ли файлы или только учитывать информацию.

Минимальный шаблон короткого сообщения:

```text
Дополнение к активной задаче.

Активная задача находится здесь:
Documentation_DayZ_Qwest/11_Задача_агенту.md

Раздел:
БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

Текущая задача:
TASK XXX — <название задачи>

Уточнение:
<текст уточнения>

До получения отчёта по задаче БЛОК 1 не переписывать. Это сообщение нужно учитывать как дополнительное пояснение к текущей задаче.
```

Если уточнение существенно меняет смысл задачи, ChatGPT должен явно указать это пользователю и предложить один из вариантов:

- дождаться отчёта агента по текущей задаче;
- отменить текущую задачу;
- переписать активный `БЛОК 1`;
- оформить отдельную следующую задачу.

## 4. Принцип жёстких рамок задачи

Этот принцип обязателен для всех будущих задач.

1. Агент не делает инициативных правок.
2. Агент не чинит "заодно" соседние проблемы, даже если они кажутся очевидными.
3. Агент не расширяет задачу самостоятельно.
4. Агент меняет только то, что прямо указано в `БЛОКЕ 1`.
5. Агент меняет только явно разрешённые файлы и разделы.
6. Если правка не указана явно и остаётся сомнительной, она считается не входящей в задачу.
7. Если агент нашёл проблему вне текущего scope, он не исправляет её сам, а фиксирует в `PROBLEMS`, `QUESTIONS` или `RECOMMENDED NEXT TASK`.
8. Если для безопасного решения кажется нужным выйти за рамки задачи, агент сначала пишет об этом в отчёте, а не меняет scope молча.

## 4.1. Legacy-код и развитие системы

Проект всё ещё строится. Старый код, старые поля и обратная совместимость сохраняются только пока они не мешают развитию системы. Если legacy мешает нормальной архитектуре или новому функционалу, нужно предлагать чистую новую схему, миграцию или удаление устаревшей части. Приоритет — рабочий функционал, понятная архитектура и развитие системы. Самовольно удалять старое без отдельной задачи нельзя.

## 4.2. Явно указывать необходимость обновления модов

Если задача меняет файлы модов и для проверки/работы требуется обновление PBO, агент и ChatGPT должны явно указать, какие моды нужно обновить:

* `Silver_77_Quests_Client` — если менялись клиентские/shared-структуры, `QuestData.c`, клиентские скрипты или данные, которые должны быть доступны клиенту;
* `Silver_77_Quests_Server` — если менялась серверная логика, серверные скрипты или runtime-обработка;
* оба мода — если менялись и структуры данных, и серверная логика.

Если менялись только JSON, документация или локальный редактор `JSON_Quvest`, нужно явно написать: “моды обновлять не нужно”.


## 5. Куда агент может писать

По умолчанию агент пишет только в чат.

Если задача явно разрешает обновление документации, агент может:

- обновить `AGENT REPORT` в `Documentation_DayZ_Qwest/11_Задача_агенту.md`;
- обновить `REVIEW / STATUS` в `Documentation_DayZ_Qwest/11_Задача_агенту.md`;
- обновить `Documentation_DayZ_Qwest/20_SplitDoc/TASK_HISTORY.md`;
- внести новые подтверждённые правила в нужный документ `SplitDoc`;
- уточнить ссылки на обязательное чтение для текущей задачи.

При этом агент не должен:

- менять запрещённые блоки или запрещённые файлы;
- дублировать одно и то же правило в нескольких `SplitDoc`, если можно выбрать один канонический документ;
- скрывать такие изменения в отчёте.

Если неясно, куда класть новое правило:

1. выбрать один наиболее подходящий `SplitDoc`;
2. при необходимости добавить перекрёстную ссылку;
3. не копировать одно правило в несколько мест без причины;
4. описать сомнение в отчёте.

## 8. Как ChatGPT должен ставить задачи

Перед постановкой новой задачи ChatGPT должен:

1. прочитать `AGENT_TASK_LOOP.md`;
2. прочитать нужные `SplitDoc` по теме;
3. учитывать внешние канонические документы проекта, если тема этого требует.

При подготовке задачи для агента ChatGPT формирует два отдельных блока:

1. Большой блок — полный `БЛОК 1` с техническим заданием для вставки в `Documentation_DayZ_Qwest/11_Задача_агенту.md`.
2. Малый блок — отдельное короткое сообщение агенту в чат после установки большого блока в `БЛОК 1`.

Малый блок обязательно содержит:

- номер и название `TASK`;
- путь к `Documentation_DayZ_Qwest/11_Задача_агенту.md`;
- указание на `БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА`;
- конкретный список документов, которые агент должен прочитать для этой задачи;
- команду выполнить только текущий `БЛОК 1`;
- при необходимости короткое уточнение к уже поставленной задаче.

Малый блок не дублирует всё техническое задание и не заменяет полный `БЛОК 1`.

Большой и малый блоки должны быть двумя отдельными цельными копируемыми блоками. Каждый из них должен копироваться одной кнопкой и не разбиваться интерфейсом на несколько фрагментов.

Новая задача рабочего цикла обязательно получает номер `TASK XXX`.

Внутри большого и малого копируемых блоков запрещены вложенные fenced code blocks с тройными обратными кавычками. Код, JSON, значения, примеры и форматы внутри задачи нужно оформлять обычным текстом, inline-кодом, списками или отступами.

Большой блок должен содержать только саму задачу без внешней пользовательской обёртки и инструкций о порядке копирования.

ChatGPT при постановке задач должен явно указывать:

1. scope задачи;
2. разрешённые файлы;
3. запрещённые файлы;
4. своё мнение / предпочтительное решение;
5. принцип жёстких рамок задачи, то есть правило, что агент не должен делать инициативных правок, не должен чинить "заодно" и не должен выходить за пределы того, что прямо разрешено в `БЛОКЕ 1`.

Если по результату работы появилось новое постоянное правило, ChatGPT должен:

1. оформить его отдельным пунктом;
2. указать, в какой `SplitDoc` его нужно внести;
3. поручить агенту внести его туда, если задача разрешает правки документации.

### 8.1. Короткий список будущих идей

Когда пользователь просит перечислить будущие идеи, направления развития, планы или возможные следующие реализации, по умолчанию давать короткий человеческий список:

- один пункт — одна идея;
- короткое жирное название;
- после тире одно-два предложения;
- без длинной технической спецификации;
- порядок можно менять по целесообразности, и он не означает обязательный приоритет;
- подробности раскрывать только после выбора пользователем конкретного пункта.

Не превращать обычный запрос «что у нас ещё есть?» в большую техническую документацию.

## 9. Как агент должен обновлять документацию

Если задача разрешает агенту писать в документы, агент обязан:

1. читать `AGENT_TASK_LOOP.md` и указанные `SplitDoc`;
2. выполнять только текущую задачу;
3. обновить `AGENT REPORT`, если это требуется задачей;
4. обновить `REVIEW / STATUS`, если это требуется задачей;
5. обновить `TASK_HISTORY.md`, если задача меняет историю состояния;
6. внести новое подтверждённое правило в нужный `SplitDoc`;
7. не дублировать правило в нескольких местах без необходимости;
8. перечислить все изменённые документы в отчёте.

После успешного выполнения задачи агент должен очистить текущую задачу из `Documentation_DayZ_Qwest/11_Задача_агенту.md`.

Очистку `БЛОКА 1` выполнять строго по каноническому алгоритму из раздела `3.2`. В этом разделе не дублировать самостоятельную версию алгоритма.

## 13.1. Один законченный шаг и минимальный контекст

По возможности один `TASK` должен решать один небольшой законченный шаг или один основной вопрос. Большая цель, общий план и следующие этапы остаются у пользователя и ChatGPT; агенту передаётся только контекст, реально необходимый для текущего шага. Если большая задача естественно делится на самостоятельные исследования, исправления или реализации, предпочитать несколько коротких последовательных `TASK` одной большой задаче и не поручать агенту заранее исследовать или реализовывать следующие этапы.

Обычная задача по возможности включает:

- один основной вопрос или результат;
- один основной файл либо небольшой набор тесно связанных файлов;
- минимально необходимый набор документов по матрице чтения, без тематических документов «на всякий случай»;
- только необходимые проверки.

Не повторять внутри `TASK` большие постоянные правила из `START` и `SplitDoc`: достаточно указать нужные документы в разделе чтения. Если для понимания шага нужна большая цель, описать её одной-двумя короткими фразами, а не переносить весь предыдущий контекст проекта.

Это не жёсткий лимит: несколько файлов или тесно связанных изменений допустимы, когда они объективно нужны для корректного решения. Цель правила — уменьшать расход контекста агента и необходимость последующего сжатия или пересборки задачи без ущерба для корректности, безопасности и необходимых проверок.

Обычный `БЛОК 1` содержит только конкретику текущей задачи:
- номер и название TASK;
- цель;
- что читать;
- что сделать;
- разрешённые файлы;
- специфичные запреты именно этой задачи;
- проверки;
- короткий формат отчёта.

Не нужно каждый раз полностью повторять:
- запрет `git commit/push/reset/clean/checkout`;
- принцип жёстких рамок задачи;
- правило очистки `БЛОКА 1`;
- общий формат отчёта;
- правило статуса чтения GitHub-репозитория;
- базовые правила агента из `START.md`.

Длинный подробный `БЛОК 1` оставлять только для рискованных задач:
- Git/history/reset;
- удаление или перенос файлов;
- восстановление исходников;
- PBO/build/AddOn Builder;
- Steam upload;
- runtime/server profile/progress;
- массовые архитектурные изменения;
- правки JSON-контракта;
- задачи с высоким риском потери данных.
