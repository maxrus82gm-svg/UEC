# SERVER PROFILE RULES

Правила для задач, связанных с dev JSON, локальным DayZ profile и реальным переносом конфигурации на сервер.

## 1. Dev source of truth

Актуальная dev-версия quest JSON находится здесь:

- `P:\Silver_77_Quests\JSON_Quvest\Silver_77_Quests.json`

Именно этот файл считать рабочим источником разработки редактора и квестов, если пользователь явно не сказал обратное.

## 2. Что не считать production

Локальный DayZ profile на машине разработки не считать production-сервером.

Например путь вида:

- `C:\Users\REX\AppData\Local\DayZ\Silver_77_Quests\Silver_77_Quests.json`

может быть тестовой локальной копией, но не главным серверным источником правды.

## 3. Кто переносит JSON на сервер

Пользователь вручную переносит готовый JSON на реальный игровой сервер.

Агентам запрещено автоматически:

- копировать quest JSON в server profile;
- копировать quest JSON в production-папки;
- считать локальный profile настоящим сервером;
- чистить `players/` или progress без прямой команды.

## 4. Что агент может делать

Можно:

- читать JSON из `JSON_Quvest`;
- проверять структуру;
- валидировать;
- сравнивать с другими копиями;
- сообщать, что серверная копия отличается;
- предлагать пользователю вручную перенести файл.

Нельзя без прямой команды:

- перезаписывать JSON в server profile;
- перезаписывать JSON на реальном сервере;
- удалять серверный progress;
- чистить server profile;
- вшивать JSON в PBO.

## 5. Как писать в отчётах

Если актуальный JSON находится в `JSON_Quvest`, писать так:

```text
Актуальная dev-версия JSON находится в:
P:\Silver_77_Quests\JSON_Quvest\Silver_77_Quests.json.
Для production-сервера пользователь переносит этот файл вручную.
```

Если синхронизация была только в локальный DayZ profile, писать так:

```text
JSON был скопирован только в локальный DayZ profile для теста. Это не считается переносом на реальный игровой сервер.
```

## 6. Единый runtime-конфиг Silver_77_Migrate

Единственный активный runtime-файл мода:

- `$profile:Silver_77_Migrate/MigrationConfig.json`.

Общие event/weather/storm-поля находятся на верхнем уровне, а независимые migration-группы хранятся объектами массива `scenarios`. Количество сценариев не хардкодится: новая группа добавляется новым объектом массива.

Существующий unified JSON runtime-код не переписывает, не пересортировывает и не дополняет текстовым патчем. Пользовательские значения и порядок сценариев сохраняются. Отсутствующие поля допускается заполнить constructor defaults только в runtime-объекте без записи файла; malformed JSON нельзя заменять defaults.

Если `MigrationConfig.json` отсутствует, runtime-код может один раз безопасно сформировать его из существующих старых `MigrationEvent.json`, `MigrationScenario_001.json` и `MigrationScenario_002.json`: сначала прочитать все найденные legacy-файлы, сохранить их значения, проверить временный unified JSON и только затем установить новый файл. Повреждённый legacy JSON блокирует автоматическую миграцию. Старые runtime-файлы не удаляются и после создания unified-конфига игнорируются.

Это правило описывает runtime-поведение самого мода. Оно не даёт агенту права самостоятельно изменять, удалять или переносить production profile пользователя.
