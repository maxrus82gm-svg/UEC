# GIT REVIEW RULES

Подробные правила Git / REVIEW для задач, где нужно проверять commit, push, историю репозитория, GitHub или риски Git в проекте `Silver_77_Quests`.

Документ читается только для задач, связанных с Git, GitHub, diff, status, commit, push, review, историей изменений или проверкой результата после отчёта агента.

Перед обычными задачами без Git и review этот документ читать не нужно.


GitHub-репозиторий:

## 2. Главное правило Git

Git контролирует только пользователь.

Агент не имеет права выполнять действия, которые меняют состояние Git-репозитория, без отдельной прямой команды пользователя.

Агенту запрещено без прямой команды пользователя:

- делать `git add`;
- делать `git commit`;
- делать `git push`;
- делать `git pull`;
- делать `git merge`;
- делать `git rebase`;
- делать `git reset`;
- делать `git clean`;
- делать `git checkout`;
- делать `git switch`;
- делать `git branch`;
- делать `git tag`;
- создавать ветки;
- переключать ветки;
- удалять ветки;
- менять remote;
- менять Git-конфиг;
- переписывать историю Git;
- откатывать чужие изменения.

Этими процессами управляет только пользователь.

## 3. Read-only Git

Read-only Git-команды можно выполнять только если текущая задача прямо разрешает Git-проверку или задача сама связана с Git / review.

Примеры read-only команд:

```bash
git status
git branch --show-current
git remote -v
git log --oneline -5
git diff --stat
git diff
```

Эти команды не должны менять файлы, индекс, ветки, remote, историю или состояние репозитория.

Если агент использовал Git-команды, он обязан указать это в отчёте.

Если Git-проверка не разрешена текущей задачей, агент не должен запускать Git-команды только из привычки.

## 4. Правило сохранности пользовательских изменений

Агент не должен перезаписывать пользовательские изменения.

Если Git-проверка разрешена и показывает незакоммиченные изменения, агент обязан:

- учитывать, что они могли быть сделаны пользователем;
- не откатывать их;
- не чистить рабочую папку;
- не выполнять reset / checkout / switch / clean;
- указать риск в отчёте, если изменения мешают текущей задаче.

Если Git-проверка не выполнялась, агент не должен утверждать, что видел локальные изменения.

## 5. Commit и push

Commit и push выполняет только пользователь, если он не дал отдельную прямую команду агенту.

Правильная формулировка в отчёте:

```text
Commit не создавался агентом.
Push не выполнялся агентом.
Git-история не изменялась агентом.
```

Нельзя писать, что commit / push выполнены, если агент этого не делал.

Нельзя предлагать commit / push как автоматическое продолжение работы агента.

## 6. REVIEW после AGENT REPORT

После каждого `AGENT REPORT`, когда пользователь просит review или сообщает, что агент выполнил задачу, ChatGPT обязан выполнить review результата до итогового вывода пользователю, если доступны репозиторий, GitHub или файлы для проверки.

ChatGPT не должен отвечать только на основании текстового отчёта агента, если результат можно проверить через доступные файлы или репозиторий.

Если проверка невозможна, ChatGPT обязан явно указать причину.

Агент-исполнитель не пишет финальный блок `СТАТУС КОММИТА` за ChatGPT.

Агент может писать только факты:

- `commit не создавался`;
- `push не выполнялся`;
- `Git-история не изменялась`;
- какие read-only проверки реально выполнялись.

Актуальный последний commit для review определяет ChatGPT после отчёта агента.

## 7. Формат начала REVIEW

Любой review после отчёта агента должен начинаться с блока:

```text
СТАТУС КОММИТА: "<commit message>"
Repository: maxrus82gm-svg/Silver_77_Quests
Branch: main
Commit: <short sha>
Проверка: выполнена / частично выполнена / не выполнена
```

Если commit message доступен, указывать именно его.

Если commit message короткий или неинформативный, например `+`, `01`, `02`, `23`, писать его как есть.

Если message не подтверждён, писать:

```text
Commit message: не подтверждён
Причина: <что помешало подтвердить>
```

## 8. Статус чтения GitHub-репозитория

Каждый раз, когда ChatGPT читает данные из GitHub-репозитория, он обязан явно указать статус чтения.

Минимальный формат:

```text
Repository:
Branch/ref:
Commit SHA:
Commit message:
Files read:
Проверка:
```

Если файл читается через default branch или `main`, нужно подтвердить текущий commit этой ветки и указать его в ответе.

Если пользователь дал конкретный hash, нужно написать, что чтение выполнено именно по этому hash.

Если commit не удалось подтвердить, указать:

```text
Commit SHA: не подтверждён
Причина: <причина>
```

Если читалось несколько файлов, перечислить ключевые прочитанные файлы.

## 9. GitHub не равен локальному Git

GitHub показывает только то, что уже попало в удалённый репозиторий.

Если изменений на GitHub не найдено, писать:

```text
Push не обнаружен.
Локальные изменения не проверялись.
```

Не утверждать, что локальных изменений нет, если проверялся только GitHub.

Если проверялся локальный репозиторий, указывать путь:

```text
P:\Silver_77_Quests
```

## 10. Структура дальнейшего review

После блока `СТАТУС КОММИТА` использовать структуру:

```text
GIT / REPOSITORY CHECK
UNEXPECTED CHANGES
REVIEW STATUS
FINDINGS
PROBLEMS
NEXT
```

`FINDINGS` должны содержать реальные найденные проблемы. Если проблем нет, написать это явно.

`PROBLEMS` должны содержать ограничения проверки, риски доступа, неподтверждённые данные или невозможность проверить commit / push.

## 11. UNEXPECTED CHANGES и служебные файлы

При GitHub / Git / diff / review-проверке нужно отдельно сверять фактические изменённые файлы со scope задачи.

Если обнаружены изменения в служебных файлах, которые не входили в scope задачи, они обязательно указываются в `UNEXPECTED CHANGES`.

Служебные файлы и папки проекта:

- `.git`
- `.vs`
- `.obsidian`
- `.vscode`
- `.gigacode`
- `bin`
- `obj`
- `.vs/*`
- `*.suo`
- `*.user`
- `*.vcxproj.user`
- workspace-файлы
- session-файлы
- cache-файлы
- временные файлы IDE

Для `Silver_77_Quests` особенно подозрительны:

- `.obsidian/*`
- `Documentation_DayZ_Qwest/.obsidian/*`
- `workspace.json`
- `graph.json`

Запрещено писать, что служебные файлы не менялись, если GitHub / Git / diff показывает, что они изменялись.

Если Git / GitHub / diff не проверялись, нельзя утверждать, что служебные файлы не менялись. Нужно писать:

```text
Служебные файлы не проверялись.
```

Если `UNEXPECTED CHANGES` содержит служебные файлы, ChatGPT должен указать это в `REVIEW STATUS` или `PROBLEMS` и предложить отдельную cleanup-задачу. Такие изменения не считаются частью выполненной задачи, если они не входили в её scope.

`.gitignore` не удаляет уже отслеживаемые файлы из Git. Если служебный файл уже tracked, для полного удаления из индекса нужна отдельная Git-задача или ручное действие пользователя.

## 12. Формат отчёта агента для Git-задачи

Если задача затрагивала Git, агент должен указать:

```text
Branch:
- текущая ветка, если проверялась

Status:
- есть ли незакоммиченные изменения, если проверялось

Changed files:
- какие файлы изменены

Diff summary:
- кратко что изменилось

Commit:
- не создавался агентом

Push:
- не выполнялся агентом

GitHub check:
- проверялся или нет
```

В отчёте нельзя выдумывать Git-данные, которые не проверялись.

## 13. Главное правило завершения

Git используется агентом только для контроля и анализа изменений, если это разрешено задачей.

Обычный порядок для Git-задачи:

1. прочитать текущую задачу;
2. выполнить только разрешённые read-only проверки;
3. понять изменения;
4. сделать разрешённую правку, если она входит в задачу;
5. выполнить разрешённую проверку;
6. написать отчёт;
7. остановиться и ждать действий пользователя.

Commit, push, pull, branch, merge, rebase, reset, clean и другие изменяющие Git-действия выполняет только пользователь без отдельной прямой команды агенту.
