# DOCUMENTATION RULES

Правила создания и обновления Markdown-документов проекта `Silver_77_Quests`.

Документ нужен, чтобы агент создавал и менял документацию аккуратно, без дублей, повреждения кириллицы и случайного переноса чужих путей.

## 1. Когда читать этот документ

Читать этот документ, если задача:

- создаёт новый `.md`-документ;
- создаёт или меняет структуру документации;
- переносит правила из одного документа в другой;
- обновляет `Documentation_DayZ_Qwest/20_SplitDoc`;
- добавляет новое постоянное правило;
- меняет правила постановки задач, отчётов, review или агентского цикла;
- предлагает новое название документа.

Если задача не создаёт документы и не меняет структуру документации, этот файл читать не нужно.

## 2. Канонические пути проекта

Рабочий проект:

```text
P:\Silver_77_Quests
```

Главная документация:

```text
Documentation_DayZ_Qwest
```

Активная задача:

```text
Documentation_DayZ_Qwest/11_Задача_агенту.md
```

Стартовые правила:

```text
Documentation_DayZ_Qwest/12_Старт_агента.md
```

Тематические правила:

```text
Documentation_DayZ_Qwest/20_SplitDoc
```

История задач:

```text
Documentation_DayZ_Qwest/20_SplitDoc/TASK_HISTORY.md
```

Очередь задач:

```text
Documentation_DayZ_Qwest/05_Очередь_задач.md
```

## 3. Главное правило

Документы создаются и обновляются только по задаче пользователя или активной задаче в `БЛОКЕ 1`.

Агент не создаёт новые правила, папки или документы по собственной инициативе.

Перед созданием или переносом документа нужно понять:

1. какой документ уже существует;
2. нет ли дубля по смыслу;
3. куда правило относится тематически;
4. какие документы нужно читать для этой конкретной задачи;
5. какие файлы текущая задача разрешает менять.

Если подходящий документ уже есть, обновлять его, а не создавать дубль.

## 4. Формат Markdown

Документ должен быть обычным Markdown-файлом.

Требования:

- расширение `.md`;
- понятный заголовок первого уровня;
- короткие разделы;
- нормальные списки;
- настоящие переносы строк;
- текст не должен быть записан одной строкой;
- не вставлять текстовую последовательность `\n` вместо настоящих переносов;
- не использовать HTML без необходимости;
- не добавлять автогенерированный мусор.

## 5. Кодировка и кириллица

Все новые и нормализованные Markdown-документы сохранять в:

```text
UTF-8 без BOM
```

Перед правкой документов с кириллицей читать:

```text
Documentation_DayZ_Qwest/20_SplitDoc/ENCODING_RULES.md
```

Русский текст нельзя повреждать.

Запрещено заменять кириллицу на:

- повторяющиеся знаки вопроса;
- кракозябры;
- транслит;
- нечитаемые символы.

Если есть сомнение в кодировке, остановиться и указать риск в отчёте.

Если при работе с Markdown кириллица повреждалась, выглядела повреждённой или восстанавливалась, действовать по аварийному протоколу:

```text
Documentation_DayZ_Qwest/20_SplitDoc/ENCODING_RULES.md
```

Восстановление кириллицы нельзя описывать одной общей фразой. В `ENCODING CHECK` и, если был риск потери смысла, в `PROBLEMS` указать файл, участок, причину, способ восстановления, источник корректного текста и проверки после восстановления.

## 6. Windows-пути

Windows-пути писать читаемо и без лишнего экранирования.

Правильно:

```text
P:\Silver_77_Quests\Documentation_DayZ_Qwest
```

Не экранировать обратные слэши двойными слэшами без технической необходимости.

Если путь находится внутри Markdown inline-code, обычный Windows-путь допустим.

## 7. Scope и запреты

Не менять без прямой задачи:

- JSON квестов;
- `QuestUI.c`;
- `QuestJournalUI.c`;
- `.layout`;
- скрипты мода;
- server profile;
- PBO/build output;
- игровые данные;
- IDE-файлы;
- служебные папки;
- реальные конфиги агентов.

Не переносить, не удалять и не переименовывать документы без отдельной прямой команды.

## 8. Правила переноса из внешних документов

При переносе правил из другого проекта нужно адаптировать смысл, а не копировать текст вслепую.

Перед завершением проверить, что в рабочих правилах проекта нет:

- чужого названия проекта;
- чужих абсолютных путей;
- чужой структуры задач;
- чужих папок шаблонов;
- чужих названий файлов, которые не относятся к `Silver_77_Quests`.

Все рабочие правила должны быть адаптированы под:

```text
Silver_77_Quests
P:\Silver_77_Quests
Documentation_DayZ_Qwest
Documentation_DayZ_Qwest/11_Задача_агенту.md
Documentation_DayZ_Qwest/20_SplitDoc
maxrus82gm-svg/Silver_77_Quests
main
```

## 9. Связь с другими документами

Если новый документ становится постоянным правилом, добавить короткую ссылку только в нужное место:

- `Documentation_DayZ_Qwest/12_Старт_агента.md`, если правило стартовое или маршрутизационное;
- `Documentation_DayZ_Qwest/11_Задача_агенту.md`, если нужна строка в матрице чтения;
- профильный `SplitDoc`, если нужна тематическая ссылка.

Не копировать полный текст правила в `START`, если есть профильный `SplitDoc`.

`START` должен оставаться коротким маршрутизатором.

## 10. Проверка перед завершением

Перед отчётом проверить:

- документ находится в разрешённом scope;
- нет дубля уже существующего документа;
- Markdown читается нормально;
- UTF-8 сохранён;
- нет BOM;
- кириллица не повреждена;
- нет повторяющихся знаков вопроса, символов замены и mojibake-фрагментов `Рџ`, `Рќ`, `Р’`, `СЃ`, `С‚`, `\uFFFD`;
- нет текстовой последовательности `\n` вместо настоящих переносов;
- нет случайных путей чужого проекта;
- не менялись запрещённые файлы.

## 11. Что писать в отчёте

Если задача создавала или обновляла документацию, в отчёте указать:

```text
CREATED FILES:
- что создано

CHANGED FILES:
- что изменено

UPDATED RULES:
- какие правила добавлены или уточнены

CHECKS:
- что проверено

ENCODING CHECK:
- UTF-8 / BOM / кириллица
```

Если менялась только документация, обязательно написать:

```text
Моды обновлять не нужно.
```
