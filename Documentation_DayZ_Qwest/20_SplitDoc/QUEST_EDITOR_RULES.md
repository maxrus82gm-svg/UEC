# QUEST EDITOR RULES

Правила для задач по `Quest JSON Editor` и dev-окружению редактора.

## 1. Роль редактора

Редактор квестов является удобной оболочкой над реальным JSON-контрактом мода.

Главное правило:

- мод является источником правды;
- редактор должен подстраиваться под мод;
- редактор не должен придумывать отдельную схему данных, которая расходится с runtime.

## 2. Рабочие папки

Основная рабочая папка редактора:

- `P:\Silver_77_Quests\JSON_Quvest`

Канонический dev JSON:

- `P:\Silver_77_Quests\JSON_Quvest\Silver_77_Quests.json`

Старт редактора:

- `P:\Silver_77_Quests\JSON_Quvest\start-editor.cmd`

Все пути редактора, JSON, backup, draft, `server.ps1`, конфигурации и вспомогательных файлов трактовать относительно `P:\Silver_77_Quests\JSON_Quvest`, если отдельным правилом явно не указано иначе.

`Support/JSON_Quvest` удалён и не является каноническим редактором. В новых задачах не выбирать пути из `Support` как рабочий editor root.

## 3. Что не считать частью runtime-мода

Файлы редактора, например `app.js`, UI редактора и вспомогательные скрипты:

- относятся к инструменту редактора;
- не являются PBO/runtime-кодом мода;
- не должны трактоваться как игровая логика сами по себе.

Если задача относится только к редактору, не нужно без причины менять клиент или сервер мода.

## 4. Правила по JSON и runtime

1. Редактор формирует JSON строго под то, что реально читает мод.
2. Не добавлять новые поля только ради удобства редактора, если мод их не поддерживает.
3. Перед расширением редактора сначала проверить runtime-код клиента и сервера.
4. Не допускать повторного расхождения между `JSON_Quvest` и альтернативными старыми копиями в `Support`.

## 5. Stack rules

`item-stack-rules.json` является важной частью редактора.

Правила:

- не удалять справочник стеков;
- не упрощать его до vanilla-значений;
- не считать, что `quantity` всегда означает число отдельных физических предметов.

Для item-objectives учитывать:

- `quantity`
- `useItemQuantity`
- `allowPartialTurnIn`
- `removeOnComplete`
- `item-stack-rules.json`

## 6. Что не ломать в концепции редактора

Считать правильными направлениями:

- `NPC Flow`;
- `Offer / Completion / Reward`;
- `Objectives` вместо выдуманного `requiredItems[]`;
- `triggerActions[].dialogText` вместо выдуманного `dialogue`;
- отдельный блок наград;
- visual split по ролям;
- stack rules.

Текущая role-driven модель `NPC Flow`:

- один блок хранит одну роль;
- `Offer` одиночный и обязательный;
- `Reward` одиночный и обязательный;
- `Completion` опционален, блоков этой роли может быть несколько;
- один NPC / trigger может участвовать в нескольких ролях только через отдельные блоки;
- редактор должен синхронизировать role-массивы, `triggerActions[]` и `trigger.questIds`.

Не переделывать визуальную концепцию редактора с нуля без отдельной задачи.

## 7. Автогенерация quest ID

При создании нового квеста редактор должен предлагать quest ID автоматически по выбранному NPC / trigger.

Правила:

- серия ID определяется по существующим квестам выбранного trigger;
- связь квеста с trigger учитывается через `offerTriggerIds`, `completionTriggerIds`, `rewardTriggerIds`, `triggerActions[].triggerId` и `trigger.questIds`;
- ID с числовым хвостом продолжается следующим свободным номером;
- ведущие нули сохраняются, например `fishman_CHO_01` -> `fishman_CHO_02`;
- если серия не найдена, используется безопасный fallback на основе `triggerId`;
- ID остаётся редактируемым вручную;
- перед сохранением проверяется, что ID не пустой и не повторяет существующий `quests[].id`;
- старые quest ID не переименовываются автоматически.
